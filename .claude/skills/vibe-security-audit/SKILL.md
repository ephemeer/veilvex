# Vibe Security Audit — 20 типовых дыр

Источник чек-листа: Instagram-ролик Джамала Багаева (@jamalozh) «20 пунктов для защиты навайбкоженного сайта» (пункты 16–20 — из комментария автора под роликом). Методика сохранена дословно, добавлены пояснения «как проверить».

## Главное правило

**Ничего не меняй, пока не показал отчёт.** Сначала аудит, потом план, потом правки по одной. Не пиши, что проблема есть, если ты её не видел в коде. Если чего-то не нашёл или не смог проверить — так и напиши.

## ЭТАП 1 — АУДИТ

Пройди по списку. Для каждого пункта напиши: **есть проблема / нет / не применимо**, файл и строку, и насколько это опасно (**критично / средне / мелочь**).

| # | Дыра | Как проверить |
|---|------|---------------|
| 1 | **Секреты в гите**: файл `.env`, ключи, пароли, токены. Проверить и историю коммитов, а не только текущие файлы. | `git log -p --all -S "API_KEY"`, `git log --all --diff-filter=A -- '*.env*'`, grep по `sk-`, `AKIA`, `ghp_`, `xoxb-`, `-----BEGIN`, `password=`; проверить `.gitignore` на `.env*`. |
| 2 | **Настоящие API-ключи в коде фронтенда.** | grep `src/`, `public/`, собранный `dist/` на ключи и токены; всё, что попало в бандл, — публичное. Публичные ключи (anon key, Maps key) должны быть ограничены по домену. |
| 3 | **В базе выключен Row Level Security** или иначе не ограничен доступ к чужим строкам. | Supabase/Postgres: `ALTER TABLE … ENABLE ROW LEVEL SECURITY` + политики на каждую таблицу; Firebase: rules не `allow read, write: if true`; ORM: фильтр по `user_id` в каждом запросе. |
| 4 | **Права доступа проверяются только на фронтенде**, а на сервере нет. | Каждый эндпоинт/серверное действие сам проверяет сессию и роль; скрытая кнопка ≠ защита. |
| 5 | **На эндпоинтах нет ограничения частоты запросов.** | Rate limit на формы, логин, OTP, платные вызовы (LLM, SMS). Хранилище лимита — не только память одного инстанса. |
| 6 | **SQL-запросы собираются склейкой строк** вместо параметров. | grep на `` `SELECT … ${`` и `" + ` в запросах; только параметризованные запросы / ORM. |
| 7 | **Нет проверки входящих данных на сервере.** | Схема (zod/valibot/joi) на каждое тело запроса, query и params; лимит размера тела; строгий Content-Type. |
| 8 | **Пользовательский текст вставляется на страницу как сырой HTML.** | grep `innerHTML`, `dangerouslySetInnerHTML`, `set:html`, `v-html`, `{@html}`; экранирование при отправке в email/Telegram/Slack (HTML/Markdown parse mode). |
| 9 | **Пароли хранятся в открытом виде или со слабым хешем.** | Только bcrypt/scrypt/argon2id; не md5/sha1/sha256 без соли. |
| 10 | **Токены авторизации лежат в localStorage.** | Сессии — в httpOnly + Secure + SameSite cookie; grep `localStorage.setItem(.*token`. |
| 11 | **Админка или служебные страницы доступны без авторизации.** | `/admin`, `/debug`, `/api/internal`, Storybook, preview-роуты, swagger — закрыты или удалены из прода. |
| 12 | **CORS выставлен в звёздочку.** | `Access-Control-Allow-Origin: *` (особенно с credentials) → конкретные origin'ы; для same-origin API CORS вообще не нужен. |
| 13 | **При регистрации не подтверждается email.** | Подтверждение по ссылке/коду до выдачи прав; защита от перебора кодов. |
| 14 | **ID предсказуемые (1, 2, 3)** и нет проверки, что объект принадлежит этому пользователю. | IDOR: в каждом запросе по id проверять владельца; для публичных ссылок — UUID/случайные токены. |
| 15 | **При обновлении в базу пишется всё тело запроса целиком.** | Mass assignment: `update(req.body)` → явный список разрешённых полей (schema `.strict()` / pick). |
| 16 | **Вебхуки принимаются без проверки подписи.** | Stripe/Telegram/GitHub и т. п.: проверять подпись/секретный заголовок, timestamp против replay, идемпотентность. |
| 17 | **В проде наружу отдаются стектрейсы и подробные тексты ошибок.** | Пользователю — общий текст; детали — только в серверные логи; `NODE_ENV=production`, выключен debug. |
| 18 | **Зависимости давно не обновлялись, есть известные уязвимости.** | `npm audit` / `pnpm audit` / `pip-audit`; lockfile в репозитории; версии закреплены; CDN-скрипты — с SRI и точной версией. |
| 19 | **Нет проверки надёжности пароля** и проверки по базам утечек. | Минимум 8–12 символов, проверка через Have I Been Pwned (k-anonymity), запрет распространённых паролей. |
| 20 | **Файлы загружаются без проверки типа, размера и имени.** | Белый список MIME по содержимому (magic bytes), лимит размера, генерируемое имя, хранение вне веб-корня / в объектном хранилище, без выполнения. |

Дополнительно (не из списка, но проверяй всегда): заголовки безопасности (CSP, HSTS, X-Content-Type-Options, X-Frame-Options/frame-ancestors, Referrer-Policy, Permissions-Policy), HTTPS-only, honeypot/антиспам на формах, SSRF при запросах по URL от пользователя, открытые редиректы.

### Формат отчёта

```
## Аудит безопасности — <проект> — <дата>

| # | Пункт | Статус | Где | Опасность | Комментарий |
|---|-------|--------|-----|-----------|-------------|
| 1 | Секреты в гите | нет | .gitignore:5, git log | — | история чистая, .env игнорируется |
| 5 | Rate limit | есть проблема | api/contact.ts:12 | критично | лимита нет |
…

Не удалось проверить: …
```

## ЭТАП 2 — ПЛАН

Отсортируй найденное по опасности (критично → средне → мелочь) и покажи, что предлагаешь править и как. **Дождись «го»** от пользователя.

## ЭТАП 3 — ПРАВКИ

Делай **по одному пункту за раз**, каждый — отдельным коммитом с понятным сообщением (`security: add rate limit to contact API`). После каждой правки проверяй, что приложение запускается и основные сценарии работают (сборка, тесты, ручной прогон формы/логина).

## ЭТАП 4 — ЧТО НЕЛЬЗЯ ПОЧИНИТЬ КОДОМ

Выпиши отдельным списком. Например: ключи, которые уже утекли в гит, надо **отозвать и выпустить заново руками** — скажи, какие именно и где это делается (панель провайдера, BotFather, консоль облака). Сюда же: включить 2FA на хостинге и в домене, настроить переменные окружения в панели хостинга, включить RLS в панели Supabase, ротация паролей.
